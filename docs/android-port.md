## iOS 대량 가져오기 위험 분석

기존 구현은 수백 명이라는 숫자 자체보다 다음 작업이 한 시점에 겹치는 것이 위험하다.

1. 가져오기 확인 화면에서 각 행의 중복 여부를 이전 행과 기존 고객 배열에서 반복 검색한다. 최악의 경우 계산량이 행 수의 제곱에 비례한다.
2. 고객 추가 후 앱의 모든 목록, 고객, 기록, 스케줄, 캠페인을 하나의 JSON 스냅샷으로 메인 스레드에서 다시 인코딩하고 원자적으로 교체한다.
3. 저장 직후 선택 목록의 모든 주소를 대상으로 좌표 변환 작업을 자동 시작한다.
4. 사진 가져오기는 원본 바이트, 임시파일, 화면용 디코딩 이미지, OCR용 회전 및 원근 보정 이미지를 동시에 보유할 수 있다.
5. OCR은 원본 크기를 유지한 채 최대 네 방향과 복수의 원근 보정 후보를 검사하므로 고해상도 다중 사진에서 순간 메모리 사용량이 커질 수 있다.

## Android 구조 원칙

- 고객과 기록은 전체 JSON이 아니라 Room/SQLite 행 단위로 저장한다.
- CSV는 스트리밍 파서로 한 행씩 읽고 최대 200명 단위로 Room에 삽입한다.
- 전체 가져오기는 하나의 DB 트랜잭션으로 처리하여 취소 또는 오류 시 일부 데이터가 남지 않게 한다.
- 중복 번호와 이름/주소 키는 `Set`으로 한 번 계산하여 평균 `O(n)`으로 판정한다.
- 파일 읽기, 파싱, DB 쓰기는 메인 스레드 밖에서 수행한다.
- 주소 좌표 변환은 가져오기 트랜잭션과 분리하고 WorkManager 큐로 지연 실행한다.
- OCR 원본은 URI/임시파일로 유지하며 화면에는 축소 썸네일만 제공한다.
- OCR은 한 번에 한 장만 처리하고 각 장이 끝날 때 이미지 버퍼를 해제한다.

`GOOGLE_MAPS_API_KEY`에서 키를 읽는다. 실제 키는 Git에 커밋하지 않는다. Google Cloud에서
`Maps SDK for Android`를 활성화하고 API 키를 패키지명 `com.lucid47.soheeyagaja`와 앱 서명
